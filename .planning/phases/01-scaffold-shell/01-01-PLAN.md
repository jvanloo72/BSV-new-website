`src/components/legal/Disclaimer.astro` props contract (D-09, D-10):
```typescript
type DisclaimerId = 'footer' | 'contact' | 'blog' | 'practice-area' | 'attorney';
interface Props { id: DisclaimerId; }
```
Build FAILS if a layout passes an id outside this union (TypeScript enforcement) OR if the id is not present in `src/content/disclaimers/disclaimers.json` (runtime build-time check). No silent fallback.

`src/layouts/BaseLayout.astro` props contract (FOUND-05):
```typescript
interface Props {
  title: string;
  description: string;
  canonical?: string;
  ogImage?: string;
}
```
Renders a named `<slot name="head" />` inside `<head>` for per-layout JSON-LD additions (Plan 03 uses this). Default `<slot />` for page body.

`src/content.config.ts` exports (FOUND-03):
```typescript
export const collections = { disclaimers /* Plan 02 adds: attorneys, practiceAreas, blog, testimonials */ };
```
Plan 02 EXTENDS this `collections` export — it does NOT replace it. The disclaimers loader uses `file('src/content/disclaimers/disclaimers.json')` (NOT a glob — the JSON file has multiple entries inline).

Disclaimer collection schema (D-08):
```typescript
schema: z.object({
  id: z.enum(['footer', 'contact', 'blog', 'practice-area', 'attorney']),
  text: z.string(),
  version: z.string(),
});
```

`src/content/disclaimers/disclaimers.json` shape: a top-level JSON array of objects, one per disclaimer id. The `file()` loader treats each array element as a separate entry keyed by the `id` field.

`vercel.json` `headers` schema (Vercel 2026-03-11 docs): array of `{ source, headers: [{ key, value }] }` objects. The `source: "/(.*)"` matcher applies the headers to every route. Plan 06 may add additional source-specific entries.

The canonical footer disclaimer text constant lives in BOTH `src/content/disclaimers/disclaimers.json` (the rendered source of truth) AND `tests/disclaimer-crawl.spec.ts` (the assertion target — Plan 00 created the constant `FOOTER_DISCLAIMER_FRAGMENT = 'The information on this website is for general informational purposes only';`). The text in disclaimers.json MUST contain this fragment verbatim — Plan 07's crawl test asserts substring inclusion.

<rationale>
The Walking Skeleton has a build-order dependency: integrations must be added via `npx astro add` rather than by hand-editing `astro.config.mjs`, because each integration registers its own setup logic (e.g., Tailwind v4 wiring goes into `vite.plugins`, NOT `integrations`; the Vercel adapter sets the `adapter` key; the order of imports in the generated config matters). The `npx astro add` commands run sequentially.

The disclaimer JSON is loaded via `file('src/content/disclaimers/disclaimers.json')` rather than `glob(...)` because all five disclaimers live in a single JSON file (per D-03). The `file()` loader treats each entry in the array as a discrete collection record keyed by the `id` field. Plan 02's other four collections all use `glob(...)` because they have one MDX file per entry.

The minimal `SiteHeader` / `SiteFooter` shipped in this plan get RE-EXPANDED in Plan 04 (which adds full nav, both office locations, copyright line, skip link, more refined visual treatment). Plan 01 only needs them to render the firm name and a single footer disclaimer so the Walking Skeleton is observable.

Critical: Astro 6's `output: 'static'` is the default. Do NOT set `output: 'hybrid'` (removed in Astro 6 per Pitfall 12). Do NOT enable `security.csp` in `astro.config.mjs` — CSP ships via `vercel.json` headers only (per Pitfall A2).

The disclaimer text seeded in this plan MUST be reviewed against `.planning/LAW_FIRM_WEBSITE_GUIDE.md` and California bar guidance. Per RESEARCH.md Assumption A8, this is checkpoint:human-verify territory before any preview deploy — Task 4's checkpoint covers this.
</rationale>
